# pdca-collection: собственный PLAN всех задач перед планированием коллекции

- **Дата:** 2026-10-06
- **Статус:** Согласована письменно в чате 2026-10-06. Design only, implementation not started. Письменный план реализации ожидает ревью пользователя и выбора метода исполнения.
- **Нормативность:** после реализации нормативными остаются активные `config/skills/**` и `config/agents/**`; исторические спеки — контекст, не исполняемый контракт.

## 1. Желание и критерии успеха

Пользователь хочет, чтобы коллекция использовала **собственный настоящий PDCA PLAN каждой
входящей задачи ДО построения DAG и любой другой коллекционной организации работ**. Это не
`scout`-анализ, выдаваемый за PLAN. Ранний PLAN — это тот же самый план задачи, который затем
исполняется; дефолтного **второго** PLAN внутри лейна нет.

Ментальная аналогия: ручной драйвер «уступает» на границе PLAN→DO пользователю; коллекция
уступает на **той же** границе коллекционному оркестратору — для группировки и расписания.
Существующая семантика standalone normal/manual и autonomous не меняется.

Инварианты успеха:

- каждая задача-вход DAG имеет **сохранённый валидный собственный PLAN**;
- **ни один** DO составляющей задачи не начинается раньше, чем выполнен all-plan barrier и
  валидное расписание;
- идентичность, состояние и ревизия задачи сохраняются при переходе в лейн;
- поздние противоречия не игнорируются.

## 2. Текущий поток и мотивирующее расхождение

Факты (точные ссылки):

- `config/skills/pdca-collection/SKILL.md:41-48` — на этапе P `scout` собирает footprint и
  зависимости, затем `planner` строит DAG и режет на группы. Это коллекционное планирование
  **без** собственного PLAN задач.
- `config/skills/pdca-collection/SKILL.md:201-210` — собственный полный PLAN задачи возникает
  **внутри уже исполняющего лейна**, то есть после DAG/групп/порядка.
- `config/agents/pdca-orchestrator.md:27-49` — вход коллекционного цикла описан как полный цикл
  на задачу; отдельной границы «сначала все PLAN, потом DAG» нет.
- `config/skills/pdca-coder/SKILL.md:786-807` — PLAN пишется на диск, normal-режим имеет
  go-gate, standalone autonomous стартует DO немедленно; явной третьей развязки (уступка
  коллекции) нет.

Желаемое поведение требует **явной передачи управления (handoff)**, а не злоупотребления
текущим запрещённым автономным пейзом. Существующий анализ footprint/зависимостей может
по-прежнему поставлять **факты** отдельному PLAN задачи, но **не** должен порождать
pre-barrier решения о DAG/группах.

## 3. Варианты и решение

**Предпочтённый вариант:** тот же цикл уступает на существующей границе PLAN→DO, сохранённое
продолжение (continuation) потребляется лейном.

**Отклонённый вариант:** специальная имитация PLAN коллекцией — отклонена, потому что
дублирует вариант-специфичные требования и не даёт собственного genuine PLAN.

Зафиксированные рамки: **нет** отдельного generic PLAN-продукта, **нет** пользовательского
CLI-флага (этой спекой не требуется), **нет** нового агента/модельного тира. Cheap-оркестратор
владеет координацией цикла; `planner` владеет планировочными решениями, `scout` — фактами,
`coder` — записью, `check` — вердиктом, `escalate` — существующими границами. Архитектор
**проектирует**, а не исполняет какую-либо коллекцию. Этот hook **коллекционно-локальный**: он
не делает произвольные standalone-autonomous пейзы законными.

## 4. Фазовый и информационный поток

1. **Bootstrap (минимальный):** регистрируются стабильные id задач, исходный бриф,
   ограничения/критерии приёмки; вариант задачи выбирается существующей маршрутизацией
   (.NET/C# → `pdca-dotnet`; другой код → `pdca-coder`; иначе → `pdca`).
2. Весь список задач передаётся как контекст для требований каждой задачи к зависимостям.
   **Никакого** предвычисленного DAG/порядка/групп.
3. **Собственный PLAN задачи:** базовый gather/decide с требованиями варианта, персистится
   `coder`.
4. **All-plan barrier → коллекционное планирование:** только после готовности **всех** задач
   авторитетные PLAN собираются, коллекционный `planner` проверяет совместимости, требования,
   footprint и нерешённую неопределённость, затем строит DAG, детектит циклы, режет на группы и
   топологически упорядочивает с существующим ограничением непересечения footprint групп.
5. Расписание персистится привязанным к **точным ревизиям PLAN** задач; выделяются
   worktree/бранчи/лейн-исполнители по существующей политике 1 vs `>=2`.
6. Сохранённые задачи возобновляются на DO после проверки применимости и исходных применимых
   гейтов.

**До barrier разрешены только:** bootstrap, индивидуальное планирование/ресёрч и статусные
артефакты. **Запрещены:** реализация задач, исполняющие лейны, execution
worktree/бранчи и решения планировщика. Родитель видит готовые задачи, но **не** освобождает
**ни одну** раньше времени.

PLAN-результат для коллекции обязан идентифицировать: планируемый footprint записи (файлы/
модули плюс обоснованная неопределённость), требования к межзадачным зависимостям, допущения/
предпосылки о выходах предшественников, ревизию PLAN задачи и базовую идентичность/ref
репозитория. Это **коллекционно-специфичные handoff-метаданные рядом** с genuine PLAN задачи,
а **не** универсальные новые обязательные поля ввода/вывода каждого standalone-варианта.
Догадки о зависимостях **не** превращаются тайно в группировку заранее.

PLAN может планироваться против ещё не реализованных выходов, если есть явные стабильные
требования. Если осмысленный валидный план невозможен без недоступных решений/результатов —
фиксируется gap и прогресс останавливается до barrier до разрешения; placeholder не объявляется
ready.

## 5. Handoff и гейты

Три поведения:

- **standalone normal:** PLAN → ожидание явного go → DO;
- **standalone autonomous:** PLAN → DO немедленно;
- **коллекционная задача:** PLAN → durable checkpoint, управление возвращается коллекционному
  родителю → barrier + валидное расписание → продолжение с DO.

Handoff — это **нормальный возврат**, а не done, failure, incomplete, abandon или поддельный
human go. «PLAN ready» означает, что содержательные обязательные выходы PLAN завершены и
персистнуты, а **не** пользовательскую авторизацию и **не** успешное завершение задачи.

Gate 1 и все существующие per-variant правила security/scope/approval/no-fourth/iteration
сохраняются. Применимый человеческий go **не может** синтезироваться завершением all-plan.
Новая интерактивная коллекционная оркестрация **не** вводится: существующий запрет драйвера на
interactive go-gated циклы **не снимается**; спека меняет только контроль границы. Там, где
применимо человеческое одобрение, вызывающая сторона следует существующей interactive
ответственности. Явно выбранный вариант задачи остаётся неизменным при возобновлении.
Возвращаемый payload — компактные refs/идентичность/ревизия плюс исход handoff; каноническое
состояние живёт на диске. Персист выполняется **до** возврата. Дополнительного второго PLAN
только из-за switch call/worktree **нет**.

## 6. Персистентность и восстановление

Статус-файл коллекции `docs/specs/status/collection-<slug>.md` остаётся истиной очереди.
Существующий жизненный цикл задачи pending/running/done/incomplete не меняется; прогресс
планирования — **отдельное** поле pending/running/ready (новый `blocked` в жизненный цикл
задачи **не** вводится). Для каждой задачи записываются: выбранный вариант, cycle ID задачи
(включая N), ссылка на канонический статус, ревизия PLAN (r), готовность планирования,
исходный baseline, handoff-ссылки зависимостей/footprint; сохраняются n и всё существующее
состояние цикла. Расписание хранит вектор ревизий task-PLAN, по которому принимались
DAG/группы.

Канонические пути статуса — вариант-специфичные: `pdca` → `.pdca/status/<task>-<N>.md`;
`pdca-coder` и `pdca-dotnet` → `docs/specs/status/<task>-<N>.md`. При `>=2` группах
сохранённое состояние должно быть доступно внутри назначенного worktree с той же
идентичностью/счётчиками/PLAN; ссылка коллекции указывает, какой **единственный** mutируемый
канонический статус является текущим. Передача/install состояния должны завершиться и
авторитетное владение/ссылка — быть персистнуты **до** DO; никогда не существует конкурирующих
записываемых статусов. Исходные копии-источники, если сохраняются, — снапшоты, а не
авторитетный текущий статус. Крэш во время передачи означает: DO нет, пока авторитет не
разрешён; нового плана по умолчанию нет. Одна группа сохраняет текущее дерево по существующей
политике. Начальная запись статус-артефактов **не** создаёт исполняющую инфраструктуру.

При возобновлении: незавершённый PLAN продолжает существующий цикл; готовые PLAN
переиспользуются при отсутствии доказанной инвалидации; DAG строится лишь когда barrier истинен;
соблюдается существующее возобновление с текущей фазы; задачи в DO/CHECK **не** переоткрываются
как PLAN только потому, что коллекция перезапустилась. Если сохранённые привязки ревизий группы
не совпадают с текущими PLAN — планировщик **не может** освобождать задачи. Пока привязанные к
расписанию ревизии не совпадают с текущими PLAN, задачи не допускаются к DO; допуск
восстанавливается только после предусмотренной §7 проверки planner (совместимость либо, до старта
лейнов, пересмотр расписания) и персистенции актуальной привязки; сам драйвер не объявляет ревизии
совместимыми.

## 7. Инвалидация и конфликты

Pre-DO целевой gather + при необходимости `planner` проверяет релевантные допущения, выходы
предшественников и выделение против фактического текущего состояния лейна; это **не** полный
обязательный планировочный проход и **не** суждение драйвера, подменяющее `planner`. Инвалидирует
релевантное evidence, **не** несвязанные изменения автоматически. Невыполненные допущения →
возврат к собственному PLAN задачи по существующим правилам replan-решения/счётчиков; **без**
замаскированного сброса/свежего N.

До начала **любого** исполнения лейна изменённые метаданные могут заставить коллекционного
`planner` явно перевалидировать/перестроить расписание, персистнуть его, и all-plan barrier
снова становится валидным. После начала исполнения **нет** автоматического
rerun/remerge/recluster/reset/revert; сохраняется существующий коллекционный запрет. Совместимые
локальные ревизии плана могут продолжаться только с evidence `planner`, что зависимости/
непересечение footprint групп/выделенный порядок остаются валидными, и с персистнутой обновлённой
привязкой; если ревизии ломают эти инварианты — небезопасное продолжение останавливается для
явного решения; **нет** молчаливого старого DAG и авто-regroup. Эта остановка — **не** общее
разрешение автоматически merge/менять исходы или перезапускать работу.

DAG-цикл, противоречивый контракт предшественника, неразрешённые пересекающиеся footprint групп
или неполный содержательный PLAN **препятствуют** освобождению. Существующие терминальные
статусы и правила конфликтов/восстановления в остальном сохраняются. Scope replacement, лимиты
итераций, права escalate — без изменений.

## 8. Параллелизм и не-цели

Строгий ALL-barrier **не зависит** от того, собираются PLAN последовательно или параллельно.
Обязательной оптимизации параллельного PLAN в первом изменении **нет**; лимит
scheduling/worker применяется как существующий после группировки. **Нет** лишних агентов,
широкого редизайна PDCA, interactive collection mode, изменений merge/common verification,
выдачи прав, model id или политики commit/push. Коммиты этой спекой **не** авторизуются;
существующие политики сохраняются.

## 9. Поверхность изменений для будущей реализации (не фактические изменения)

- активный коллекционный скилл (P, лейн, статус, отношение к базовым вариантам);
- `config/agents/pdca-orchestrator.md` — task-boundary вход/результат + поведение продолжения;
- узкое уточнение PLAN→DO в `pdca`/`pdca-coder`/`pdca-dotnet`: правки документируют контекст
  коллекционного вызывающего/handoff и **сохраняют** исполняемое поведение standalone normal и
  standalone autonomous циклов; новый standalone pause mode и новый interactive collection mode
  **не** вводятся, коллекционный handoff не принимается за запрещённый standalone-autonomous пейз;
- `docs/pdca-guide.md`, `docs/articles/pdca-collection.md`;
- генератор `config/skills/pdca-collection/assets/diagram/gen_collection.py` и сгенерированные
  ассеты.

Не предполагать наличие активных API в коде: в первую очередь это **текстовые контракты**
скиллов/агентов. Текущие тесты `config/skills/pdca-collection/tests/test_verification_recovery.py`
плюс новые контрактные проверки/сценарии P/PLAN barrier; существующее покрытие регрессии C
сохраняется. Поздний sync по правилам репозитория — только при реализации, не сейчас.

## 10. Матрица приёмки/тестов

- (a) все собственные PLAN варианта завершаются и персистятся до DAG, даже если одна задача
  закончила раньше;
- (b) исполняемая задача использует тот же PLAN/r/N, без принудительного второго PLAN;
- (c) один невалидный/отсутствующий содержательный PLAN препятствует DAG/DO, gap записан;
- (d) крэш после частичного планирования возобновляет завершённые ready-PLAN без повтора;
- (e) крэш после групп/checkpoint-передачи возобновляет корректное каноническое состояние до DO;
- (f) изменения предшественника инвалидируют допущения → replan, без молчаливого устаревшего
  исполнения;
- (g) изменения footprint/зависимостей до лейнов → расписание пересматривается; после лейнов →
  несовместимость останавливает, без авто-recluster;
- (h) неизменённый standalone normal по-прежнему требует go, а autonomous — немедленный DO;
- (i) контракт evidence .NET и обязательные PLAN-требования каждого варианта сохранены;
- (j) смешанные вариант-специфичные статус-пути разрешаются корректно;
- (k) отрендеренный диаграммный поток показывает собственный PLAN всех задач и ALL barrier до
  DAG и до старта DO в лейнах;
- (l) существующие тесты merge/verification recovery без изменений.

Различать текстовые/регрессионные контрактные тесты и реальные runtime multi-agent трейсы;
статических утверждений недостаточно, чтобы доказать поведение. Стратегия тестирования включает
репрезентативный scenario-trace с проверкой порядка событий и тех же сохранённых cycle refs, где
есть harness; при отсутствии harness фиксируется ручная проверка сценария, и не заявляются
выполненные проверки. Для этой spec-only задачи тесты **не** запускаются.

## 11. Передача и следующий шаг

**История одобрения.** 2026-10-06 пользователь одобрил в чате **письменную** спецификацию
(design only). Реализация **не** начата; коммиты/push не авторизованы. Письменный план
реализации подготовлен и ожидает ревью пользователя и выбора метода исполнения — до любой
реализации. Дизайн-решения этого документа при фиксации одобрения не изменялись.

Одобрение разговорного дизайна покрывало только написание спеки, не реализацию. Далее требуется
отдельное письменное одобрение плана реализации и выбор метода исполнения — до любой
реализации. Commit/push нет. Placeholder'ов/нерешённых нормативных требований нет;
синтаксис реализации явно оставлен будущему плану. Ссылки на источники выше и на предыдущие
design-доки verification/recovery остаются минимальными.
