# Восстановление после провала общей верификации C в pdca-collection

> **Superseded (2026-10-02, user-approved v2).** Решение ниже про отдельную стадию
> `TRIAGE`, узел `BLOCKED` и условную recovery-панель **заменено**: общая верификация `C`
> — это **стандартный CHECK** (`pdca-dotnet`: Gather cheap → вердикт `check` medium,
> `config/agents/check.md`). Отдельного triage-этапа/`BLOCKED`-узла нет; отсутствующий
> отчёт → стандартный **re-gather**; FAIL реального дефекта → стандартная корректирующая
> задача, её ACT → полный `C`. Дальнейший текст сохранён как **история дизайна** и не
> переписывается; актуальный контракт — `config/skills/pdca-collection/SKILL.md` и отчёт
> `.superpowers/sdd/2026-10-01-pdca-collection-verification-recovery-plan/check-owner-v2/report-v2.md`.

Дата: 2026-10-01. Репозиторий: `opencode-config`. Дизайн-спека: только решения, реализации нет.

## Контекст

- `config/skills/pdca-collection/SKILL.md` (разделы «C — верификация», «Сбой»,
  «Статус коллекции», «D — инфраструктура, трекинг, merge») исполняет общую верификацию C
  в основном дереве через `coder`. Провал C («Регресс build/тестов/покрытия/перфа») лишь
  блокирует закрытие — **маршрута восстановления нет**. Это и есть пробел.
- Каждая задача группы — полноценный `config/skills/pdca-dotnet/SKILL.md`-цикл: скилл
  коллекции **не переопределяет** его state machine, гейты и правила ревизии/попыток
  `r`/`n/3`; правила эскалации одного и того же дефекта живут в базе.
- База `pdca-dotnet` **не знает коллекционного понятия `incomplete`** (у неё состояния
  единиц `pending`/`running`/`blocked`/`done`/`superseded`). Коллекционный `incomplete` —
  только словарь этого скилла; в базу он не привносится.
- В `config/skills/pdca-collection/assets/diagram/gen_collection.py` (state graph внутри
  `render`, ~строки 297–324) есть неподдерживаемые маршруты уровня коллекции:
  `C → DO` («регресс build/тестов») и `C → PLAN` («gate C не пройден · ре-план»).
- Барьер merge: при `>=2` группах ждать **все** лейны терминальными (`done`/`incomplete`
  с явным исходом), затем последовательно мержить каждый успешный tip; готовность —
  терминальность, не успех; на `incomplete` не ждём бесконечно. Одна группа — текущее
  дерево/бранч, без collection-worktree, group/task-веток и merge.
- Существующие перечисления статусов **не меняются**:
  группа `pending | in-progress | done | incomplete | merged`; задача
  `pending | in-progress | done | incomplete`. Слова `blocked`, `re-gather`,
  `unverified` **не добавляются** в эти перечисления — они именуют состояние
  **общей верификации**, а не статус группы/задачи.

## Решения

1. **Шаг 1 — сырые доказательства.** `coder` (cheap) собирает фактические доказательства
   провала C: команда, exit code, лог, числа — без интерпретации и без правок кода.
2. **Шаг 2 — триаж `check` (medium).** `check` различает: (а) реальный дефект
   интегрированного результата; (б) отсутствующий/недостоверный отчёт; (в) сбой
   окружения. Отсутствующий отчёт или сбой окружения → состояние общей верификации
   **blocked**, **правок кода нет**; после восстановления окружения/получения
   доказательств — **повтор всей** общей C, включая повторный триаж нового провала.
   Это **не** ремонт кода и **не** повод слепо засчитать дефект как провал CHECK.
   Бесконечных автоматических опросов/ретраев нет: если восстановить не удаётся —
   блокер остаётся записанным в состоянии верификации. Транскрипт/корневые evidence
   исходного сбора сохраняются.
3. **Шаг 3 — корректирующая задача.** Подтверждённый дефект становится
   **корректирующей задачей** с обычным `pdca-dotnet` PLAN→DO→CHECK→ACT и **собственным
   статус-файлом**, **связанным** из статуса родительской коллекции. Работа идёт на
   **текущем интегрированном дереве/бранче**, успешные результаты сохраняются. Никаких
   автоматических перезапусков групп, повторных merge/recluster, reset/revert и новых
   collection-worktree/цепочек веток. Корректирующие задачи — **отдельные записи/ссылки,
   а не дополнительные лейны**. Любой разворот/реструктуризация — только явным планом,
   с сохранением доказательств; молча выбрасывать работу нельзя.
4. **Роли не изобретаются.** Primary коллекции делегирует уже существующие роли по
   стандартному контракту (`coder`/`scout` cheap, `planner`/`check`/security medium,
   `escalate` strong); `lane` — не решающий. Новый контроллер PDCA не вводится;
   «mixed» — композиция workflow, **не** четвёртый уровень моделей.
5. **Шаг 4 — возврат в C.** После PASS/ACT корректирующей задачи управление возвращается
   родительской C и перезапускаются **все** обязательные общие гейты, а не только упавший
   тест.
6. **Шаг 5 — закрытие.** Только PASS общей C разрешает успешный ACT/cleanup коллекции.
   Неразрешённая корректировка оставляет коллекцию с состоянием верификации
   **unverified**/blocked (причина, доказательства, статус, сохранённые worktree для
   продолжения); **успех корректирующей задачи сам по себе не означает успех коллекции**.
   Пока C красная — **нет** успеха и cleanup.

## Поток управления

```text
общая C FAIL → coder: сырые доказательства → check (medium): триаж
  ├ реальный дефект → корректирующая задача (pdca-dotnet P→D→C→A)
  ├ отчёт отсутствует/недостоверен → blocked (состояние верификации); правок кода нет
  └ сбой окружения → blocked (состояние верификации); правок кода нет
      └ окружение восстановлено/evidence получены → повтор ВСЕЙ общей C (+ новый триаж)
  → PASS/ACT корректирующей задачи → возврат в родительскую C → повтор ВСЕХ общих гейтов
      ├ PASS → общий A/cleanup
      └ FAIL → снова триаж (история дефектов сохраняется)
```

Сбор доказательств/перепроверка окружения — **отдельная** ветка от ремонта кода. Прямые
безусловные маршруты `C → DO` и `C → PLAN` (начальная кластеризация) из диаграммы
удаляются. Новые семантические маршруты: `C → TRIAGE` (`FAIL`), `TRIAGE → REPAIR`
(`defect`), `REPAIR → C` (`full-verification`), `TRIAGE → BLOCKED`
(`environment-or-evidence`), `BLOCKED → C` (`restored`), `C → A` (`PASS`),
`A → EXIT` (`finalized`). Узел `A` — это **ACT родительской коллекции** (отчёт,
разрешённый cleanup, финализация), реальный узел state-графа, а не колонка и не пустой
дубль. Локальный ACT корректирующей задачи возвращает управление в родительскую `C`
(`REPAIR → C` `full-verification`) и **не** прыгает в `A`/`EXIT`. Маршруты `C → EXIT`,
`REPAIR → A`, `REPAIR → EXIT` и `BLOCKED → REPAIR` запрещены. Все обязательные узлы
(`START`,`P`,`DO`,`C`,`A`,`EXIT`,`TRIAGE`,`REPAIR`,`BLOCKED`,`ESCALATE`,`INCOMPLETE`)
перечисляются вместе; `A` достижим (`C → A`), сирот/пустых дублей нет.

## Общая верификация и восстановление (статус)

В статус-файл коллекции
`docs/specs/status/collection-<slug>.md` добавляется подраздел
**«Общая верификация и восстановление»** со следующими полями:

- последний результат общей C + пути к evidence (команда, exit code, лог, числа);
- причина блокировки (нет отчёта / сбой окружения / подтверждённый дефект) и состояние
  верификации (`blocked` / `unverified` / `pass`);
- **defect id** и **история**: применённые фиксы и результаты C после каждого
  (идентичность дефекта сохраняется между закрытиями/перезапусками корректирующей задачи);
- ссылка на статус-файл связанной корректирующей задачи;
- **следующий разрешённый шаг**.

Подраздел описывает состояние **общей верификации**, а не статус группы/задачи. Перечисления
групп/задач при этом **не расширяются** (см. «Контекст»).

## Восстановление окружения и отсутствующих отчётов

- Сбой окружения или отсутствующий/недостоверный отчёт → в состоянии верификации
  записывается **blocked**, **правок кода нет**.
- Новый сбор идёт только когда окружение восстановлено или evidence доступны; затем
  повторяется **вся** общая C (не только упавший тест), и при новом провале — снова триаж.
- **Никакого неограниченного автоматического опроса/ретраев**: невосстановимый блокер
  фиксируется как блокер и остаётся в статусе; транскрипт и корневые evidence исходного
  сбора сохраняются.
- `blocked`/`re-gather`/`unverified` — **не** ремонт кода и **не** повод считать дефект
  провалом CHECK; это отдельная ветка от `REPAIR`.

## Эскалация, ревизии и STOP

- Внутри корректирующей задачи действует **стандартная** политика ревизий/попыток базы
  `pdca-dotnet`; отдельный счётчик попыток коллекции **не вводится**.
- Если **тот же** дефект общей C повторяется после одного фикса — `escalate` **до второго
  фикса** (даже если локальный CHECK задачи прошёл и создан новый статус-файл/новый task
  id). История дефекта и `r`/`n` живут в статусе и **не сбрасываются** сменой сессии/task
  id. Исчерпанная ревизия **не получает четвёртого CHECK реализации даже после
  `escalate`**; продолжение возможно **только** через реально пересмотренный план
  (новую ревизию `r+1`) с фактически изменёнными задачами/зависимостями/действиями при
  сохранении исходного критерия. Переименование/переформулировка или сброс — не новая
  ревизия.
- **STOP корректирующей задачи** подчиняется базовым правилам. Если `escalate` не может
  выдать допустимый пересмотренный план/STOP: **сохраняются** неразрешённый статус,
  evidence и интегрированная работа; **нет** ни успеха, ни cleanup. **Родительская
  коллекция остаётся `unverified`** (состояние верификации), а исходные задачи коллекции
  сохраняют **прежние** статусы — они не помечаются `done`/`incomplete` задним числом.
- Обобщённого «правила трёх провалов C на уровне коллекции» **нет** и не вводится.

## Барьер merge и предохранители

- `>=2` групп: ждать **все** лейны терминальными (включая `incomplete` с явным исходом),
  затем последовательно мержить **каждый успешный** tip; готовность — терминальность,
  не успех. Одна группа: merge **пропускается** (текущее дерево/бранч), ветки не создаются.
- Merge-конфликт: `git merge --abort` → `escalate` (strong), другие группы не трогаются;
  отдельный бокс конфликта в MERGE **не дублируется**.
- Сохраняются текущие бейджи: `lane`/`coder` cheap, `planner`/`check`/security medium,
  `escalate` strong; эскалация merge-конфликта отрисована отдельно.

## Критерии приёмки

1. Первый реальный дефект C маршрутизируется в `check` (medium), затем в стандартный PDCA
   на интегрированном результате; частичные/окруженческие ошибки не вызывают правок кода,
   а после локального PASS корректирующей задачи повторяются **все** общие гейты C.
2. Повторный тот же дефект эскалируется до второго фикса; смена task id не сбрасывает
   историю; нет неявного rerun/remerge/rollback; STOP сохраняет `unverified` и прежние
   статусы исходных задач.
3. Статус содержит подраздел «Общая верификация и восстановление» с полями выше;
   перечисления групп/задач **не расширены**.
4. При `>=2` группах — барьер «все лейны терминальные» с последовательным мержем только
   успешных tip; при одной группе merge пропускается.
5. В диаграмме нет неподдерживаемых прямых `C → P`/`C → DO`; есть
   `C → TRIAGE`/`TRIAGE → REPAIR`/`REPAIR → C`/`TRIAGE → BLOCKED`/`BLOCKED → C` и
   обязательный успех `C → A`/`A → EXIT`; узлы `A`/`C` реальны и достижимы;
   семантические атрибуты висят на реальных узлах/стрелках; XML и HTML SVG сохраняют
   паритет; тесты ловят удаление ребра `REPAIR → C`.
