# Skill: pdca-collection

# Коллекция задач как PDCA

## Роль

Ты ведёшь **коллекцию задач** — верхний уровень над `pdca-dotnet`. Загружай
`pdca-dotnet` вместе с этим скиллом: база (state machine, гейты, роли) не
дублируется и не переопределяется. Коллекция = список задач, разбитый на группы.

Ты (primary-оркестратор) **не правишь файлы и не запускаешь команды сам**.
Инфраструктуру (worktree, ветки), `git merge --no-ff` и обязательные проверки задачи
исполняет `coder` по твоей команде; ты ведёшь трекинг, гейты и решение о merge.

Запуск предполагает режим **явно разрешённого автокоммита** (иначе ветка задачи не
получит закоммиченного tip, от которого ветвится следующая). Коммиты в ветках
`collection/**` и `merge --no-ff` разрешены исключением `pdca-collection` в
`AGENTS.md`; вне этого режима правила «no commits unless explicitly asked» и
«never merge» действуют.

## Коллекция (P / D / C / A)

### P — кластеризация

1. Вход: список задач в любом виде, задаёт пользователь.
2. `scout` собирает footprint (затронутые файлы/модули) и зависимости между задачами.
3. `planner` строит DAG и режет на группы: группа = связная компонента/линия по
   зависимостям и общим файлам; footprint групп не пересекается; внутри группы
   задачи упорядочены топологически.
4. Группы и порядок фиксируются в файле статуса коллекции (см. «Статус»).

Если получилась **одна группа** — не падать: деградация к одному лейну. **Worktree и
ветка группы не создаются**: работаем в **текущем** worktree на текущем бранче,
коммиты (в режиме автокоммита) идут прямо в него, `merge --no-ff` не нужен —
мержить нечего; барьер merge (§D.3) и ветки группы/задач **не применяются**. Если независимых задач нет вовсе — обычный pdca-цикл; пустой вход →
сообщить, что делать нечего.

### D — инфраструктура, трекинг, merge

1. Через `coder`: по worktree на группу
   `<repo>-worktrees/<collection-id>/<group>` и ветка `collection/<id>/group-<g>`.
   **Если группа одна** — worktree и ветки (`group-<g>`, `task-<g>-<k>`) не
   создаются: работаем в **текущем** worktree на текущем бранче, коммиты идут туда
   же; вместо `merge --no-ff` — обычная работа на месте (мержить нечего).
2. `lane`-агенты запускаются параллельно (по одному `Task` на группу), не больше
   `cap` одновременно. При одной группе — один `lane` в текущем worktree.
3. **Барьер merge**: при `>=2` группах merge начинается только когда **все** лейны
   терминальны (`done` | `incomplete` с явным исходом) — готовность = терминальность,
   **не** успех. Тогда `coder` последовательно выполняет `git merge --no-ff` для **каждого
   успешного** tip (сообщение начинается с `#<n>` для issue-задачи); `incomplete` без
   успешного tip не мержится. **Работающий лейн не мержится рано.** При **одной** группе
   merge/worktree/ветки не создаются (см. §P). Если merge конфликтует — `coder` делает
   `git merge --abort`, группа **эскалируется**: `escalate` (strong) принимает решение —
   разрешить вручную, переставить порядок или пометить группу `incomplete`; другие группы
   не трогаются; гейт `C` не пройден, пока конфликт не разрешён.

   **Конфликт merge — повторный merge через оркестратор.** `escalate` (strong) — не
   исполнитель: он никогда сам не правит файлы, не запускает и не спавнит `coder` — только
   возвращает решение. Ответ эксперта — **не** успех merge. При решении «разрешить вручную»
   или «переставить порядок» оркестратор возвращает управление в MERGE и **сам** диспетчит
   `coder` на повторный `git merge --no-ff` **незамерженного** tip (после
   `git merge --abort`), разрулить конфликт по решению и завершить merge. Порядок можно
   менять только у **ещё не интегрированных** групп; ранее смерженный tip (например `G1`)
   не трогается — никаких повторных merge уже интегрированных tip, rerun/reset/revert/remerge
   групп и сброса успешных результатов. После успешного повторного merge продолжаются
   **остальные pending/eligible** merge; **полный** CHECK родительской коллекции выполняется
   только когда все выбранные успешные tip интегрированы, активного конфликта и
   незавершённого merge-состояния нет. Повторный конфликт снова → `git merge --abort` и
   `escalate` заново (без нового счётчика попыток: базовые `r`/`n` не вводятся). Решение
   «пометить `incomplete`» явно возвращает управление в MERGE и продолжает интеграцию
   остальных eligible tip по существующей политике `incomplete` (успешный tip — да, без
   tip — нет).
4. Ты ведёшь статус: задача `done` | `incomplete`; группа `done` | `incomplete` | `merged`.

### C — верификация (стандартный CHECK)

Общая верификация коллекции — это **штатный CHECK `pdca-dotnet`** (два такта:
Gather cheap → вердикт `check` medium; вход и формат вердикта — `config/agents/check.md`,
структура — `config/skills/pdca-dotnet/SKILL.md` §CHECK), а **не** отдельный
bespoke-этап коллекции. Когда все лейны остановлены, в основном дереве: все успешные
группы смержены (включая повторный merge после конфликта, §D.3) и **нет незавершённого
merge-состояния**.

Оркестратор **всегда** — даже когда все проверки зелёные — собирает через существующих
`coder`/`scout` обязательные отчёты о сырых измерениях (тесты — универсально, плюс
проверки, заданные типом работы — сборка/линтер для кода, рендер/превью для дизайна и
презентаций, замеры производительности если hot path и т.п.: команда, exit code, лог) и
отчёты review-линз, и передаёт **агрегат** `check` (medium). Сырые измерения команд **никогда** сами не решают gate PASS: вердикт `C`
(`pass`/`fail` + findings) выдаёт `check`; `check` не запускает руки и не правит код.

- **PASS** → разрешён общий ACT коллекции (§A).
- **FAIL · реальный дефект** → оркестратор открывает **стандартную корректирующую
  задачу `pdca-dotnet`** (PLAN→DO→CHECK→ACT) на **текущем интегрированном дереве/бранче**
  с **собственным связанным статус-файлом**; её ACT возвращает управление в **полный**
  родительский CHECK — перезапускаются **все** обязательные общие гейты, а не только
  упавший тест. Дешёвый вердикт без корректирующей задачи не допускается.
- **Нет обязательного отчёта / недостоверный отчёт / сбой окружения** → стандартный
  **re-gather** (повторно собрать недостающий отчёт); это **не** дефект кода и **не**
  повод править код. Состояние общей верификации может остаться `blocked`/awaiting-reports
  в существующем статусе, но **отдельного bespoke-протокола** (третий вердикт, отдельный
  stage/узел) нет.

Никаких автоматических rerun/remerge/recluster/reset/revert и новых
collection-worktree/цепочек веток; корректирующие задачи — **отдельные записи/ссылки, а не
дополнительные лейны**. Пока `C` красная — **нет** успеха/cleanup, результаты сохраняются.

Правила ревизий/эскалации внутри корректирующей задачи — **базовые `r`/`n/3`**
(`config/skills/pdca-dotnet/SKILL.md` §State machine, §Escalation): тот же дефект после
одного фикса → `escalate` **до второго фикса** даже при локальном CHECK=PASS и новом task
id; смена task id/сессии/статус-файла **не** сбрасывает `r`/`n`/историю дефекта; исчерпанная
ревизия **не** получает 4-го CHECK реализации даже после `escalate` — продолжение только
через реально пересмотренный план `r+1`. Отдельного счётчика попыток коллекции и
обобщённого «правила трёх провалов `C` на уровне коллекции» нет. При STOP без допустимого
пересмотренного плана сохраняются неразрешённый статус/evidence/интегрированная работа;
родительская коллекция остаётся **`unverified`**, исходные задачи — с **прежними**
статусами; **успех корректирующей задачи сам по себе не означает успех коллекции**.

Это **не** смешивается с механизмом `incomplete` задачи внутри лейна (§Лейн, §Сбой): тот
относится к сбою отдельной задачи группы и решению `planner` в её цикле, тогда как STOP
корректирующей задачи — про повтор дефекта **общей** `C` и подчиняется базовым `r`/`n`.

### A — завершение

Только **PASS общей `C`** разрешает завершение. Отчёт (группы, задачи, ветки,
merged/incomplete, evidence, результат корректирующих задач); `coder` сносит worktree и
временные ветки; закрытие/удаление файла статуса. Push — никогда.
Если `escalate` не выдаёт допустимого пересмотренного плана/STOP, сохраняются
неразрешённый статус, evidence и интегрированная работа: **нет** успеха и cleanup,
родительская коллекция остаётся **`unverified`**, а исходные задачи коллекции сохраняют
**прежние** статусы. **Успех корректирующей задачи сам по себе не означает успех
коллекции.**

## Лейн (work stream)

Субагент `lane` исполняет **одну** группу в своём worktree (абсолютные пути, `cd`); work stream: один параллельный поток работ на группу, worktree per group.
Для каждой задачи по порядку:

1. ветка `collection/<id>/task-<g>-<k>` от закоммиченного tip предыдущей;
2. полный цикл `pdca-dotnet` (PLAN→DO→CHECK→ACT) с делегированием
   planner/coder/check/escalate;
3. автокоммит после задачи — иначе следующая не ветвится от закоммиченного
   результата. Коммитируй **только файлы задачи** (`git add <paths>`), не
   `git add -A`: иначе заберёшь чужие/артефактные файлы.

`lane` **не принимает решений** — только оркеструет план: не решает, что задача
невыполнима/не готова/независима, не выбирает объём и не судит результат; любой вопрос
адресует `planner` (PLAN), а не пользователю. Статус `incomplete` — следствие сбоя или
невозможности по контракту (§Сбой), а не суждение лейна.
Источник истины очереди — файл статуса коллекции (§Статус): `lane` перечитывает его на
старте и после каждой задачи, берёт первую задачу со статусом `pending` в
зафиксированном порядке и обновляет её статус; промпт запуска передаёт **путь к файлу**,
а не перечисление задач — так очередь переживает компакцию контекста и перезапуск.
Правила: ветка задачи — единица коммита (worktree на задачу не создаётся); сбой
задачи → управление получает `planner` (PLAN), который либо возвращает в DO, либо закрывает задачу как `incomplete` (patch + причина в статусе), и лейн идёт дальше — пайплайн не стопается; результат группы =
tip последней закоммиченной задачи (ветка группы `collection/<id>/group-<g>`
ff-продвигается на него); лейн возвращает компактную сводку ≤8 строк без
кода/диффов/логов.

## Git-модель

Пример (инстансы `group-A`/`task-A-1` — это `group-<g>`/`task-<g>-<k>`):

```text
current-branch
├─ merge --no-ff collection/<id>/group-A   (worktree A: task-A-1 → task-A-2 → task-A-3)
└─ merge --no-ff collection/<id>/group-B   (worktree B: task-B-1 → task-B-2)
```

- 1 worktree на группу; ветка группы `collection/<id>/group-<g>` ff-продвигается
  на tip каждой завершённой задачи и в конце равна tip последней.
- **Одна группа**: изоляция не нужна — ни worktree, ни веток группы/задач; коммиты
  идут прямо в текущий бранч, `merge --no-ff` не выполняется (см. §P/§D).
- Внутри группы — цепочка веток задач `collection/<id>/task-<g>-<k>`; следующая
  ветвится от tip предыдущей.
- Ветки группы и задач — **сиблинги**, не вкладываются друг в друга: git не
  допускает ref, являющийся префиксом другого ref.
- Интеграция — при `>=2` группах **после терминальности всех лейнов**: `git merge --no-ff`
  каждого **успешного** tip, по одному, последовательно (§D.3).
- Конфликт merge → `git merge --abort`; `escalate` (strong) только возвращает решение
  (сам не правит и не запускает `coder`), а повторный `git merge --no-ff` незамерженного tip
  выполняет `coder` по диспетчу оркестратора (§D.3); ранее интегрированные tip не трогаются;
  gate `C` не пройден, пока все выбранные успешные tip не интегрированы.
- Push — никогда.

## Сбой (failure semantics)

| Событие | Поведение |
|---|---|
| Задача не проходит CHECK | **не стоп:** управление → `planner` (PLAN); PLAN решает — починить (loop-back в DO) либо закрыть задачу как `incomplete` (тогда `coder` сохраняет текущие изменения задачи как patch, возвращает дерево к последнему зелёному tip, в статусе пишет причину + путь к patch); лейн идёт к следующей задаче, пайплайн продолжается |
| Группа завершилась частично | её успешный tip (если есть) мержится при выполненном барьере merge (§D.3); в отчёте — incomplete |
| Merge-конфликт группы | `git merge --abort` → **`escalate`** (strong) решает (разрешить/переставить/`incomplete`), но не исполняет и не запускает `coder`; оркестратор возвращает в MERGE и диспетчит `coder` на повторный `git merge --no-ff` незамерженного tip; ранее интегрированные не трогаются; gate `C` не пройден, пока все выбранные успешные tip не интегрированы |
| Регресс обязательных проверок/артефактов задачи | gate `C` не пройден; → §C: агрегат обязательных отчётов → вердикт `check` (medium) → стандартная корректирующая задача, re-gather отсутствующего отчёта или `blocked`-состояние; коллекция не закрыта |
| Отсутствующий/недостоверный обязательный отчёт или сбой окружения | **не** дефект кода: правок кода нет; условие общей верификации → **`blocked`**; исходный транскрипт/evidence сохраняются; после восстановления окружения/получения доказательств — повтор **всей** общей `C`; без неограниченных авто-опросов/ретраев |
| Повтор того же дефекта после одного фикса | `escalate` **до второго фикса** (даже при локальном CHECK=PASS корректирующей задачи и новом task id); смена task id/сессии/статус-файла **не** сбрасывает `r`/`n`/историю дефекта |
| Исчерпанная ревизия / STOP без пересмотренного плана | 4-го CHECK реализации нет даже после `escalate`; продолжение только по реально пересмотренному плану `r+1`; иначе сохраняются неразрешённый статус/evidence/интегрированная работа, нет успеха/cleanup, родительская коллекция **`unverified`**, исходные задачи — **прежние** статусы |
| Лейн вернул «нет результата» | группа = incomplete, merge не делается |

## Статус коллекции

Файл: `docs/specs/status/collection-<slug>.md`. Содержит:

- вход (список задач) и `collection-id`;
- таблицу групп: id, задачи, порядок, worktree, ветка, статус
  (`pending` | `in-progress` | `done` | `incomplete` | `merged`);
- таблицу задач: id, группа, ветка, статус
  (`pending` | `in-progress` | `done` | `incomplete`), причина + путь к patch для
  `incomplete`, ссылка на статус-файл задачи;
  merge — на уровне группы, у задачи не бывает статуса `merged`;
- решения фаз коллекции (кластеризация, merge-стратегия);
- подраздел **«Общая верификация и восстановление»** — состояние **общей верификации**, а
  не статус группы/задачи; перечисления групп/задач при этом **не** расширяются:
  - последний результат общей `C` + пути к evidence (команда, exit code, лог, числа);
  - причина блокировки (нет отчёта / сбой окружения / подтверждённый дефект) и состояние
    верификации (`blocked` | `unverified` | `pass`);
  - **defect id** и **история**: применённые фиксы и результат `C` после каждого
    (идентичность дефекта сохраняется между закрытиями/перезапусками корректирующей задачи);
  - ссылка на статус-файл связанной корректирующей задачи;
  - **следующий разрешённый шаг**;
- Done / Verified / Incomplete.

## Отчёт

Формат — как в `pdca-dotnet` §ACT (обычный режим): что сделано, чем проверено,
что осталось/заблокировано, следующий шаг. В автономном режиме — без сообщения
для пользователя.

| Параметр | Дефолт |

| Локация агента | глобальная `~/.config/opencode/agents/lane.md` |

## Связь с pdca-dotnet

- Скилл **не переопределяет** state machine и гейты `pdca-dotnet`; он добавляет
  уровень над ними.
- Каждая задача внутри группы = полноценный цикл `pdca-dotnet` (свой статус-файл,
  свои гейты, свои роли).
- Роли (`planner`, `coder`, `check`, `escalate`, `scout`) — те же; новых ролей
  нет, кроме агента-обёртки `lane`.
- Восстановление после провала `C` (стандартный CHECK), корректирующая задача и состояние
  общей верификации — §C и §Статус («Общая верификация и восстановление»); правила
  ревизий/попыток/эскалации — база `config/skills/pdca-dotnet/SKILL.md`
  (§State machine, §Escalation), без переопределения и без коллекционного счётчика.
  Базовое коллекционное `incomplete` в базу **не** добавляется.

## Fallback

Если harness запрещает субагенту вызывать `Task` (нет вложенной делегации), `lane`
не может оркестрировать pdca. Триггер: запуск `lane` падает с ошибкой инструмента
`Task`/недоступности субагента. Тогда — плоский primary: primary сам ведёт «в
полёте» по одной задаче каждой группы (Task'и на coder/check), по завершении
запускает следующую задачу той же группы; группы прогрессируют параллельно без
lane-агентов.
