# Правила работы в этом репозитории

Снимок конфигурации opencode существует в трёх копиях, и они не должны расходиться
независимо. Направление правок всегда одно:

```
skills repo (~/sources/skills, локально ../skills)  →  opencode-config (этот репо)  →  ~/.config/opencode (хост)
     источник скиллов/плагинов                          снимок + вендоринг              только выкат
```

## 1. Хост не правим

- `~/.config/opencode/**` — **выкат**, не источник. Ничего не редактируем там напрямую:
  ни скиллы, ни плагины, ни агентов, ни профили, ни `AGENTS.md`. «Быстрая проверка на живой
  копии» тоже запрещена — проверяем в песочнице (`opencode-config-sandbox`) или отдельным
  профилем/`OPENCODE_CONFIG`.
- Агент **никогда не раскатывает** изменения в хост сам: ни хук, ни тест, ни вендоринг,
  ни коммит не пишут в `~/.config/opencode`. Выкат — отдельное явное действие по просьбе
  пользователя (см. §3), после коммита и пуша снимка.
- Найденную в хосте правку нельзя «легализовать» копированием в репозиторий: она либо
  переносится в источник осознанно и проходит обычный порядок, либо отбрасывается.

## 2. Скиллы и плагины — только в репозитории skills

Источник скиллов и плагинов — `github.com/AlexeyShirshov/skills`
(локальный клон: **`/home/alex/sources/skills`**, от этого репозитория — `../skills`):

```
skills/<skill>/             →  config/skills/<skill>/
opencode/plugins/<plugin>/  →  config/plugins/<plugin>/
```

Порядок для любой правки скилла или плагина:

1. правим **только** в `../skills` = **`/home/alex/sources/skills`**;
2. тестируем там же:
   ```bash
   OPENCODE_CONFIG_REPO=/home/alex/sources/opencode-config \
     python3 -m unittest discover -s skills/<skill>/tests -p 'test_*.py'
   ```
3. коммитим и пушим в skills repo (пуш — человеком или по явной просьбе);
4. только после этого — вендоринг в снимок:
   ```bash
   bun config/tools/vendor-skills.mjs --fix
   ```
   `--fix` откажется работать, если в источнике есть незакоммиченные правки или HEAD не
   запушен: в снимок попадает только протестированный, закоммиченный и запушенный код.
5. коммитим снимок в этом репозитории.

`config/skills/**` (кроме `habr-article`, он ставится из skills.sh и в skills repo не живёт) и
перечисленные в `config/tools/vendor-skills.mjs` плагины —
**вендоренная копия**. Править их здесь нельзя: `--check` увидит расхождение с источником
и упадёт с exit 1. Список вендоренного и пин коммита — в `skills.lock.json` (корень репо,
создаётся `--fix`, коммитится вместе со снимком).

Новый скилл/плагин в снимке = новый элемент `ITEMS` в `config/tools/vendor-skills.mjs`,
после того как он появился в skills repo.

## 3. Выкат в хост — отдельное явное действие

- Выкат выполняется по прямой просьбе пользователя, не автоматически и не «заодно»
  с коммитом. Команды — README §Восстановление (rsync снимка + `sync-profiles.mjs --fix`
  для профилей, `patch-superpowers.mjs` после обновления плагина superpowers).
- Отставание хоста от снимка — нормальное состояние, а не ошибка: `vendor-skills --check`
  печатает его как `PENDING DEPLOY` и ничего не копирует.

## 4. Проверки перед коммитом

```bash
bun config/tools/vendor-skills.mjs --check    # скиллы/плагины: снимок == skills repo
bun config/tools/sync-roles.mjs --check       # config/agents: зеркало role-assets (канон — в skills repo)
bun config/tools/sync-profiles.mjs --check    # config/profiles → installed профили
```

Плюс тесты скиллов, если менялись они (шаг 2 выше). Красный `--check` означает, что
правка сделана не в источнике — чинить в источнике, а не подгонять копию.

## 5. Где что менять

| Что | Где источник | Куда попадает |
| --- | --- | --- |
| скиллы, плагины | skills repo | `config/skills`, `config/plugins` (только `vendor-skills --fix`) |
| `config/AGENTS.md`, агенты, профили, команды, `cli.json`, `tools/` | этот репо | хост (только явный выкат) |
| `dot-agents/`, `home/`, `data/` | этот репо | `~/.agents/`, `~/`, память MCP (только явный выкат) |
